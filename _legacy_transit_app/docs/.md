# 탈수있나 FSD Frontend Architecture Directive v1.0

> 목적: 현재 `data_insight` 프론트엔드를 Feature-Sliced Design(FSD) 기반으로 재구성하기 위한 팀 구현 규약을 정의한다.  
> 기준 코드 확인일: 2026-05-27  
> 현재 코드 상태: `src/App.tsx`, `src/components/InteractiveMap.tsx`, `src/data.ts`, `src/types.ts`, `src/index.css`, `src/main.tsx` 중심의 단일 앱 구조  
> 핵심 지시: 단순 파일 분리가 아니라, UI/상태/도메인/스타일/설정값/캐시/목업/스키마의 위치와 금지사항을 명확히 하여 운영 가능한 프론트엔드 구조로 전환한다.

---

## 0. 현재 코드베이스 기준 진단

현재 `src`는 다음 파일만 존재한다.

```text
src/
├─ App.tsx
├─ components/
│  └─ InteractiveMap.tsx
├─ data.ts
├─ index.css
├─ main.tsx
└─ types.ts
```

이 구조는 MVP 시연에는 빠르지만, 기능이 늘어날수록 다음 문제가 커진다.

| 문제 | 현재 위치 | 왜 문제인가 |
|---|---|---|
| 화면/상태/도메인/API가 한 파일에 집중 | `App.tsx` | 한 기능 수정이 전체 앱 회귀로 이어진다. |
| 지도 UI와 지도 로직이 결합 | `InteractiveMap.tsx` | 레이어/줌/역 선택/렌더링 최적화가 서로 영향을 준다. |
| mock 데이터와 도메인 로직이 섞임 | `data.ts`, `App.tsx` | 실제 API provider로 교체하기 어렵다. |
| 색상, z-index, spacing, shadow가 JSX class에 직접 박힘 | `App.tsx`, `InteractiveMap.tsx`, `index.css` | 디자인 일관성과 유지보수성이 떨어진다. |
| storage key, query key, API endpoint, schema 위치가 정해져 있지 않음 | 미정 | 기능 추가 시 문자열 중복과 캐시 불일치가 생긴다. |
| `components/`가 큰 바구니 역할 | `src/components` | shared UI와 제품 기능 UI가 구분되지 않는다. |

따라서 이 프로젝트의 다음 리팩토링 목표는 “컴포넌트 분리”가 아니라 **FSD 레이어를 기준으로 코드의 거주지를 재정의하는 것**이다.

### 0.1 현재 패키지 전제

현재 `package.json` 기준으로 React Query, zod, Playwright는 설치되어 있지 않다. 따라서 이 문서의 `query-client`, `queryKeys`, `schemas`, 브라우저 자동 검증 항목은 **즉시 import 가능한 구현물이 아니라 목표 구조와 도입 규칙**이다.

| 항목 | 현재 설치 여부 | 처리 원칙 |
|---|---|---|
| React Query 계열 | 미설치 | 공공데이터/서버 상태 연동 직전에 도입 여부를 결정한다. |
| zod 등 schema validator | 미설치 | schema 디렉터리만 먼저 규정하고, 실제 validator는 API 연동 단계에서 결정한다. |
| Playwright/agent-browser | 미설치 | 우선 수동 smoke checklist를 사용하고, 자동화는 별도 의존성 추가 후 진행한다. |
| Tailwind CSS | 설치됨 | 토큰 CSS와 함께 사용하되, 매직 넘버 class 증식을 금지한다. |

## 1. 아키텍처 원칙

### 1.1 기본 원칙

이 프로젝트는 다음 FSD 레이어로 재구성한다.

```text
app → pages → widgets → features → entities → shared
```

의존 규칙:

```text
상위 레이어는 하위 레이어에만 의존한다.
하위 레이어는 상위 레이어를 import하지 않는다.
같은 레이어의 다른 slice 내부 구현을 직접 import하지 않는다.
slice 외부 접근은 public API(index.ts)를 통해서만 한다.
```

### 1.2 레이어별 책임

| 레이어 | 책임 | 둘 수 있는 것 | 두면 안 되는 것 |
|---|---|---|---|
| `app` | 앱 실행, provider, global style, layout shell | `AppShell`, providers, router, global CSS import | 제품 기능 로직, mock 데이터 |
| `pages` | 실제 화면 조립 | `MapPage`, `ArchivePage`, `SettingsPage` | API 호출, 도메인 계산, 긴 class 분기 |
| `widgets` | 독립적인 큰 화면 블록 | 지도 패널, 리포트 시트, AI 챗 패널, 아카이브 캘린더 | storage key, query key, API endpoint 직접 문자열 |
| `features` | 사용자 액션 단위 | 역 선택, 레이어 토글, 경로 생성, 리포트 저장, AI 질문 전송 | 전체 페이지 레이아웃 |
| `entities` | 제품 도메인 객체 | station, route, report, preferences, chat-message 모델 | 앱 provider, 라우팅 |
| `shared` | 비즈니스 독립 공용 기반 | UI primitive, token, config, lib, schema, mock infra | 제품 전용 상태/액션 |

### 1.3 페이지의 역할

페이지는 조립만 한다.

허용:

```tsx
export function MapPage() {
  return (
    <AppShell>
      <TransitMapPanel />
      <ReportSheet />
      <AiChatPanel />
    </AppShell>
  );
}
```

금지:

```tsx
const presets = [...];
const zIndex = 9999;
const STORAGE_KEY = "talsu.preferences.v1";
const response = await fetch("/api/chat");
```

## 4. 절대 금지사항

### 4.1 페이지/위젯 내부 하드코딩 금지

다음 값은 page/widget/feature UI 내부에 직접 쓰지 않는다.

| 금지 대상 | 예시 | 대체 |
|---|---|---|
| 색상 hex | `#0A84FF`, `#FF3B30` | CSS token `var(--color-accent)` |
| z-index 숫자 | `z-40`, `z-[100]`, `9999` | `var(--z-overlay)`, `zIndex.toast` |
| spacing px | `p-3`, `top-[52px]`, `bottom-[64px]` | layout token 또는 layout component |
| storage key | `"talsu.preferences.v1"` | `STORAGE_KEYS.preferences` |
| query key | `["routes", start, end]` | `queryKeys.routePlans(params)` |
| API endpoint | `fetch("/api/chat")` | `chatApi.sendMessage()` |
| mock 배열 | `const presets = [...]` | `shared/mocks` 또는 entity fixture |
| schema literal | 컴포넌트 내부 zod schema | `shared/schemas` 또는 entity schema |
| 긴 variant 분기 | JSX 내부 삼항 연쇄 | variant 함수 또는 style map |

### 4.2 import 금지 규칙

| 위치 | 금지 import |
|---|---|
| `shared` | `entities`, `features`, `widgets`, `pages`, `app` |
| `entities` | `features`, `widgets`, `pages`, `app` |
| `features` | `widgets`, `pages`, `app` |
| `widgets` | `pages`, `app` |
| `pages` | 다른 page slice 내부 |

허용 예:

```ts
// features/save-report/model/create-saved-report.ts
import { ReportType } from "@/entities/report";
import { RoutePlan } from "@/entities/route";
import { createId } from "@/shared/lib/id";
```

금지 예:

```ts
// shared/ui/button/Button.tsx
import { RoutePlan } from "@/entities/route";

// entities/report/model/report.ts
import { showToast } from "@/features/toast";
```

### 4.3 public API 규칙

각 slice는 외부에 `index.ts`만 노출한다.

```text
entities/report/
├─ model/
│  ├─ types.ts
│  ├─ create-report.ts
│  └─ constants.ts
├─ ui/
│  └─ ReportStatusBadge.tsx
└─ index.ts
```

외부 import:

```ts
import { createSavedReport, ReportStatusBadge } from "@/entities/report";
```

금지:

```ts
import { createSavedReport } from "@/entities/report/model/create-report";
```

| Toast | `shared/ui/toast` |
| Card | `shared/ui/card` |
| ScrollArea | `shared/ui/scroll-area` |

### 6.2 primitive 설계 원칙

- 비즈니스 문구를 포함하지 않는다.
- `ReportType`, `RoutePlan` 같은 제품 타입을 import하지 않는다.
- variant는 semantic하게 둔다.

예:

```ts
type ButtonVariant = "primary" | "secondary" | "danger" | "ghost";
type ButtonSize = "sm" | "md" | "lg" | "icon";
```

금지:

```ts
type ButtonVariant = "deadlineReport" | "boardingBus";
```

제품 전용 variant는 feature/widget에서 조합한다.

## 7. config/string/schema/caching 중앙화

### 7.1 storage keys

`src/shared/config/storage-keys.ts`

```ts
export const STORAGE_KEYS = {
  preferences: "talsu.preferences.v1",
  savedReports: "talsu.savedReports.v1",
  onboarding: "talsu.onboarding.v1",
} as const;
```

금지:

```ts
localStorage.setItem("talsu.preferences.v1", value);
```

허용:

```ts
localStorage.setItem(STORAGE_KEYS.preferences, value);
```

### 7.2 API endpoints

`src/shared/config/routes.ts`

```ts
export const API_ROUTES = {
  chat: "/api/chat",
  transit: {
    stationContext: "/api/transit/station-context",
    routePlans: "/api/transit/route-plans",
  },
} as const;
```

금지:

```ts
fetch("/api/chat");
```

허용:

```ts
httpClient.post(API_ROUTES.chat, body);
```

### 7.3 query keys

`src/shared/config/query-keys.ts`

```ts
export const queryKeys = {
  routePlans: (params: unknown) => ["routePlans", params] as const,
  stationContext: (stationName: string) => ["stationContext", stationName] as const,
  savedReports: () => ["savedReports"] as const,
} as const;
```

### 7.4 schemas

`src/shared/schemas`에는 비즈니스 독립 공통 schema만 둔다.

`entities/*/model/schema.ts`에는 해당 entity schema를 둔다.

예:

```text
shared/schemas/common.ts
entities/report/model/schema.ts
entities/route/model/schema.ts
entities/station/model/schema.ts
```

금지:

```tsx
function SettingsView() {
  const schema = z.object({ ... });
}
```

## 9. 상태 관리 규칙

### 9.1 상태 종류

| 상태 | 예시 | 위치 |
|---|---|---|
| UI local state | sheet open, hovered station | 해당 widget/feature 내부 |

## 10. 계층별 구현 지시

### 10.1 app

역할:

- feature button 로직

### 10.2 pages

역할:

- 페이지 단위 조립
- route param을 widget/feature에 전달
- page-level suspense/error boundary

두지 말 것:

- style token literal
- mock data
- API fetch
- localStorage 접근
- zod schema 생성

### 10.3 widgets

역할:

- 큰 UI 블록
- 여러 feature/entity UI 조합

예:

```text
widgets/transit-map-panel
widgets/report-sheet
widgets/ai-chat-panel
widgets/archive-calendar
widgets/settings-form
```

규칙:

- widget은 feature action을 props로 받거나 feature public API를 사용한다.
- widget 내부에서 shared primitive를 사용한다.
- widget 내부에 mock 배열을 만들지 않는다.

### 10.4 features

역할:

- 사용자에게 의미 있는 액션 하나.

예:

| feature | 액션 |
|---|---|
| `select-station` | 출발/도착역 선택 |
| `toggle-map-layer` | 지도 레이어 on/off |
| `generate-route-plan` | 조건 기반 경로 후보 생성 |
| `save-report` | 현재 플랜을 저장 리포트로 저장 |
| `send-ai-chat` | 질문 전송 및 추천 반영 |
| `complete-onboarding` | 온보딩 완료 |

규칙:

- feature는 entity 모델을 조작할 수 있다.
- feature는 page layout을 알면 안 된다.
- feature 내부 API는 `index.ts`로만 공개한다.

### 10.5 entities

역할:

- 도메인 객체의 타입, schema, 변환, UI badge.

예:

```text
entities/report/
├─ model/
│  ├─ types.ts
│  ├─ create-saved-report.ts
│  ├─ status.ts
│  └─ mock.ts
├─ ui/
│  └─ ReportStatusBadge.tsx
└─ index.ts
```

규칙:

- entity는 feature를 몰라야 한다.
- entity UI는 작은 표시 컴포넌트까지만 허용한다.

### 10.6 shared

역할:

- 비즈니스 독립 기반.

포함:

- UI primitive
- token
- config
- lib
- api client
- common schema
- common type
- mock infra

금지:

- `ReportType` 전용 버튼 variant
- `RoutePlan` 생성 로직
- `탈수있나` 특정 액션명

## 13. 캐싱/서버 상태 전략

현재는 React Query가 설치되어 있지 않다. 실제 공공데이터 연동 전에는 다음 중 하나를 결정한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| React Query 도입 | 서버 상태/캐시/재시도 표준화 | 의존성 추가 |
| 간단 custom cache | 가볍다 | 기능 증가 시 재구현 비용 |

권장:

- 공공데이터 연동을 할 경우 React Query 계열 도입.
- query key는 반드시 `shared/config/query-keys.ts`에서 생성.
- page/widget에서 query key 배열 직접 작성 금지.

캐시 정책 초안:

| 데이터 | stale time | cache time | 비고 |
|---|---:|---:|---|
| station context | 60초 | 5분 | 역 주변 상태 |
| bus boarding status | 15초 | 1분 | 실시간성 높음 |
| metro crowding | 60초 | 5분 | 추정/패턴 가능 |
| bike availability | 30초 | 2분 | 따릉이 대여소 |
| saved reports | local first | local first | Phase 8 전까지 localStorage |

## 15. Definition of Done

FSD 마이그레이션 작업은 각 PR/커밋 단위로 다음을 만족해야 한다.

- 상위 레이어가 하위 레이어만 import한다.
- page/widget 내부에 금지된 하드코딩이 새로 추가되지 않는다.
- 새 상수는 `shared/config` 또는 entity/feature model에 위치한다.
- 새 mock은 page/widget에 위치하지 않는다.
- 새 API endpoint 문자열은 `shared/config/routes.ts`에 위치한다.
- 새 storage key는 `shared/config/storage-keys.ts`에 위치한다.
- `npm run lint` 통과.
- `npm run build` 통과.
- UI 변경이면 최소 수동 smoke check 수행.
- 관련 FSD 문서 갱신.

## 17. 최종 지시 문장

앞으로 이 프로젝트에서 프론트엔드 코드를 추가하거나 수정할 때는 다음 문장을 기준으로 판단한다.

> 페이지는 조립만 한다. 위젯은 화면 블록만 맡는다. 기능은 사용자 액션만 맡는다. 엔티티는 제품 도메인만 맡는다. shared는 제품을 모르는 공용 기반만 맡는다. 색상, spacing, z-index, endpoint, storage key, query key, schema, mock data는 페이지와 위젯 내부에 직접 쓰지 않는다.

이 규칙을 어기는 코드는 동작하더라도 구조적으로 실패한 코드로 본다.
